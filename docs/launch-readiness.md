# DeepHaus launch hardening

This change implements the account/data protection foundation, reconciliation protocol, opt-in whole-library media downloads, and automated release checks. It is **not a production or App Store release certification**. Launch migrations have been applied to the isolated staging branch. No production migration, deployment, live account deletion, purchase, or restore was performed.

### Running staging locally

The public staging configuration is in ignored `.env.launch-staging.local` (mode 0600). Set **the staging project's** `SUPABASE_SERVICE_ROLE_KEY` there; never paste it into chat or use the main project's key. The runner rejects another project's legacy service JWT and clears inherited production environment values.

1. `pnpm launch:seed` creates two isolated, email-confirmed fixture accounts without sending email, and saves generated credentials in ignored `.env.launch-fixtures.local`. It enables reconciliation for only the owner fixture. Existing fixture files are preserved; inspect partial setup before retrying.
2. `pnpm launch:web` starts staging on port **3100**, with `.next-launch` and a separate TypeScript config. The normal web/API server stays on port **3000**; the isolated staging native app uses port **3100**.
3. `pnpm launch:test` runs the browser journeys. `LAUNCH_PUBLIC_ONLY=1 pnpm launch:web` allows synthetic/credentialless checks while the server credential is unavailable; authenticated API work still needs the server credential.
4. Stop the port-3100 server before `pnpm launch:build`; both staging commands use `.next-launch`. Restart it afterward. These commands leave the normal `.next` dev artifacts alone.

For the iOS simulator, run `pnpm launch:seed-native` once, then `pnpm launch:ios:build-release` and `pnpm launch:ios:open-release`. This installs `com.deephaus.app.staging` alongside the normal app and does not need Metro. Keep the staging API on port 3100. For Debug development, use `launch:ios:build`, `launch:mobile` (Metro 8083), and `launch:ios:open`. Recovery validation uses the bundled Release build because Expo's Debug launcher can intercept terminated-app deep links.

With Maestro installed, `pnpm launch:maestro` uses the separate native fixture file; `pnpm launch:native-recovery` creates and removes a temporary recovery account. Override `MAESTRO_BIN` if needed. Generated flow secrets are private temporary files; ignored test artifacts remain local. These commands do not send recovery emails. Native fixtures must remain separate from browser fixtures because global sign-out revokes other sessions.

`pnpm launch:start` serves the isolated production web build after `launch:build`. Set `E2E_PRODUCTION_SERVICE_WORKER=1` when running the service-worker journey against this server; it is skipped in development. Never run the staging development server and staging build/start against `.next-launch` simultaneously.

The benchmark page `/launch-benchmark` is available only when the launch runner's server flag is present. It uses synthetic data and is a 404 in the normal app.

## Delivered behavior

- Server authorization uses verified `getUser()` identity only. Invalid credentials return 401; verification outages return 503. Costly routes share an atomic per-account quota across sessions and personal tokens.
- Mobile preserves a separate credential-free local account identity through refresh failures and offline restarts, with a reauthentication screen for uploading saved work. Explicit sign-out clears that identity. Web also remembers a local owner for offline routing and preserves its replica on spontaneous auth expiry; this does not bypass server authorization or make an uncached web app shell available offline. Mobile recovery handles PKCE and implicit callbacks, deduplicates concurrent code exchanges, reports invalid links, and provides password completion.
- Rich-text edits reach draft persistence immediately, without a second debounce that could discard edits on card switches. Both editors serialize saves per account/card, keep drafts on device, recover drafts when reopened, avoid applying stale save responses, and offer Retry save. Mobile task persistence is keyed by account; providers reset task state on account changes and stop polling after unmount. Web task requests pin the original token and omit ambient cookies; resumable web/native uploads stop on account changes.
- Deletion returns 202/pending after saving a durable request. Database write fences prevent further account writes, including in-flight upload races. The extraction worker drives retries. Storage cleanup repeatedly removes pages until every supported bucket is empty; only then is the authentication record deleted. Failures retain the retry record.
- Study and Cram uploads preserve unique review events, retain the latest answer's saved schedule, break time ties with mutation UUIDs, clamp future timestamps, and retain history-only answers. Raw answer time, effective time, server receipt and clock adjustment are recorded. Review uploads pin the original account's JWT; account changes and expired credentials cannot acknowledge someone else's queue.
- Undo/redo references an exact study review UUID and keeps audit history; web, local and database metrics exclude undone events. Legacy queued review payloads remain decoded. Rejected/conflicting transactions stay queued instead of being discarded.
- Shared media management discovers all owned cards, prioritizes due-card images, persists progress by account, resumes unfinished items, and checks that downloaded images decode, and verifies files before reporting readiness or grading offline cards. Native files live in application documents; browser files live in account-specific CacheStorage. Native bulk downloads default to Wi-Fi and pause when connectivity policy changes. Original source documents remain online workflows.
- Web and native renderers use managed images when downloaded. Cards without required images are deferred; an entirely unavailable queue gives an actionable message.
- API requests have a 15-second read / 30-second mutation deadline, including body consumption. Reads may retry once within the same deadline. Mutations are not automatically retried by transport. Review fallback reuses its mutation ID and original answer timestamp.
- Recoverable screen error boundaries report exceptions through PostHog with release IDs. Shared scheduling counts, save serialization, polling, media state, and generation-quality evaluations reduce duplicated behavior.

## Supported offline matrix

| Environment | Card data/reviews | Managed media | App restart offline |
|---|---|---|---|
| Expo Go | Online only | Disabled | Not supported |
| Native dev/App Store build with PowerSync | After initial sync | Internal flag, Wi-Fi default; cellular opt-in | Must pass real-device gate below |
| Production web with PowerSync/service worker | After initial sync | Internal flag, CacheStorage and persistence request | Subject to browser storage and app-shell availability |
| Local web development | Replica available when configured | Can exercise the queue | Service worker is disabled; not a release test |

Data, downloaded media, and pending uploads are reported separately. A fully downloaded library can be available offline while reviews await upload. Browser eviction invalidates media readiness on verification. Supported card media currently means the image formats understood by the existing card/occlusion renderers. Unsupported audio/video markup is not silently treated as a supported download feature.
